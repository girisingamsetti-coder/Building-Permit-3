REVIEW AND REDESIGN THE DASHBOARD ARCHITECTURE FOR EVERY USER ROLE IN THE
LTP APPROVAL / BUILDING PERMIT MANAGEMENT SYSTEM.

IMPORTANT:
This is NOT only a UI redesign.

Implement BOTH:

1. ROLE-BASED DATA VISIBILITY
2. CLEAN, CONSISTENT, WELL-ALIGNED DASHBOARD UI

The dashboard must show only the data that is relevant and authorized for
the currently logged-in user.

Do not expose unrelated project, application, officer, financial, workflow,
RFI, worklog, or other operational data across roles.

==================================================
1. CORE PRINCIPLE
==================================================

The system must follow:

LOGIN
↓
USER
↓
ROLE
↓
PERMISSIONS
↓
PROJECT / APPLICATION SCOPE
↓
DASHBOARD DATA
↓
KPI / CHART / TABLE / CARD

Every dashboard component must respect this scope.

Do NOT build one global dashboard and simply hide a few cards.

Each role must receive the correct data set first, and the UI must render
from that scoped data.

==================================================
110. DATA DEFINITIONS
==================================================

Document the definition of each KPI/chart internally.

For example:

Total Applications:
number of applications within current scope.

In Progress:
applications not in terminal state.

Approved:
final approved applications.

Delayed:
applications with SLA breach.

At Risk:
applications approaching configured SLA threshold.

Do not count a completed application as delayed simply because its historical
processing time exceeded an SLA unless the metric explicitly means
"completed late".
